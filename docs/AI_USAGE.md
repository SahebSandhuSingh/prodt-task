# AI Usage Documentation

## My Approach

Before touching any code, I went through the task requirements myself to make sure I thoroughly understood what was being asked. I then used Claude to research design patterns that fit a multi-supplier integration problem, evaluate whether Temporal was the right tool for managing the booking lifecycle, and sequence the work so later steps wouldn't require rebuilding earlier ones. 

This upfront research and planning shaped the overall structure before implementation began: isolating vendors behind an adapter pattern, maintaining a clean separation between search and booking, and using Temporal specifically to meet the strict failure-handling criteria.

## Planning and Building the Backend

For each of the five backend steps, I used Claude to turn research into a concrete implementation plan, then worked with Antigravity to implement each step against that plan.

I reviewed every implementation plan myself before approving it. Several plans were sent back with specific issues to resolve before code was written:

- The mock supplier failure-injection method needed to use constructor parameters rather than environment variables to avoid flaky, order-dependent unit tests.
- A workflow edge case where an ambiguous supplier polling timeout could incorrectly resolve to `CONFIRMED` instead of falling through to `REQUIRES_MANUAL_REVIEW`.
- An unreferenced `asyncio` background task in the search service that risked being silently garbage-collected before finishing its audit database write.

Catching these during review prevented silent flaws from entering the codebase. I also read through the generated code myself—particularly the Temporal workflow and its Saga compensation logic—since that carries significant weight in the evaluation.

## Frontend

The single-page web app was generated by Antigravity based on a detailed brief outlining the customer journey, visual style, and exact backend endpoints required. After it was built, I reviewed the code to confirm no backend files or business logic had been modified, and verified that the complete customer flow—searching, booking, tracking live status, and cancelling—worked correctly end to end.

## Verification

Rather than relying on high-level summaries claiming the system worked, I required verification from a clean state: a fresh git clone with no cached dependencies and containers rebuilt from scratch. This included inspecting real terminal output from actual search requests, actual bookings, forced supplier failures, and the full test suite execution.

## Decisions I Made Myself

Some choices came down to engineering judgment calls that AI tools flagged but couldn't resolve on their own. For instance, I had to decide whether `run.sh` or `docker-compose` should be the primary documented startup path, and figure out how to address the fact that Temporal's standalone dev-server image isn't available through a public Docker registry pull. I made these calls directly rather than defaulting to whatever the tool suggested.
